# 全覆盖模型：让「所有操作」都可程序化、可观测、可闭环

> **本文与 `OPERATION-MODEL.md` 的分工**：那份回答「一条命令该长什么样、怎么落地」，
> 这份回答「**是否真的覆盖了所有操作**，以及 AI 如何据此自我改进」。
> 前者是**纵向**（单条命令的深度），后者是**横向**（全部操作的广度 × 闭合回路）。
>
> **一句话**：任何一个用户能做的操作，代码路径上必须先经过一个可被程序调用的处理器；
> UI 事件只负责把输入翻译成命令参数，不直接改状态、不直接调底层 API。

---

## 1. 为什么需要这一层（以及为什么不能靠模拟输入）

早期做法是让 AI 模拟鼠标点击。这条路在**原理上**就不成立，不是实现得不好：

| 维度 | 模拟点击 | 结构化命令 |
|---|---|---|
| 依赖 | 像素坐标、DPI、窗口遮挡、焦点 | 无 |
| 本地化 | 文案一变就失效 | 名字稳定 |
| 时序 | 弹层/异步不可控，需 sleep 猜 | 同步返回或明确事件 |
| 断言强度 | 只能看「界面亮了」 | 可读回真实状态 |
| 证明力 | 坐标碰巧命中时，逻辑错了也「通过」 | 逻辑错就失败 |

**最关键的是最后一行**：模拟点击有**假通过**风险。一个测试如果能在功能坏掉时仍然绿灯，
它不是测试，是装饰。

同理排除快捷键：快捷键是**输入绑定**，改键位即失效；命令是**意图的名字**，与绑定无关。
AI 应当接「意图层」，永不接「输入层」。

## 2. 四种原语（所有操作的完备划分）

不管功能多复杂，都归入这四类。这个划分的价值在于：**每类都有对应的验证模板**，
于是「可验证」不靠人想，靠类型决定。

| 原语 | 定义 | 典型操作 | 验证模板 |
|---|---|---|---|
| **Action** | 产生状态变更，可审计 | 复制、移动、删除、重命名、新建、排序、切视图、改设置、锁定标签、删书签 | 执行 → 读回 → 断言 |
| **Query** | 只读，无副作用 | 列目录、读选中集、读设置值、读书签树、读标签列表 | 幂等：连调两次结果相同 |
| **Navigation** | 把应用定位到可程序描述的位置 | 打开目录、切标签、打开设置页某节、定位到某文件 | 定位后 Query 能命中 |
| **Event** | 状态变化后向外推送 | 选中变化、文件变更、操作完成、错误、设置变更 | 触发 Action 后能收到 |

**「打开设置并定位到某开关」= Navigation + Query；「启用/关闭」= Action；「判断是否正常」= Query + Event + 断言。**

四类之外没有第五种。任何「这个操作归哪类都不合适」的情况，通常说明它被拆得不够细
（例如「批量重命名」是 Action，但它的预览是 Query）。

## 3. 覆盖的判据（怎么证明「所有」而不是「大部分」）

「所有操作都结构化」这句话**不可证伪**，除非给出可机械检验的判据。三条，缺一不可：

### 3.1 正向：能做的都能调（人 → 结构化）

界面上的每个动作都必须有对应命令。

**判据**：扫描菜单/按钮源码里的文案与动作号，凡未登记到覆盖表的即报错。
已落地为 `tools/check_ai_meta.py` 第 16 项（含「源码反查」子步骤 16b）。

**为什么必须扫源码而不是查登记表**：只查表时，新增一个菜单项而忘了登记，
检查会静默通过——那正是缺口重新长出来的方式。源码反查让「漏登记」当场失败。

### 3.2 反向：能调的都能做（结构化 → 人）

暴露给机器的每条命令，人必须也能触发（键盘/面板/界面）。

**判据**：`aiExposed` 且无必填参数的命令，命令面板覆盖；有必填参数的必须登记人工入口
（参数来自拖放/输入框/勾选）或提供确定式替代。已落地为第 15 项（R20）。

### 3.3 双向都不允许「隐式上下文」

依赖「用户当前选中了什么」的操作，不得暴露给机器——机器只知道「我想删 A」，
不知道「用户此刻选中 B」，暴露即等于让它猜。已落地为第 4 项。

> 三个判据合起来，才能说「覆盖」。缺 3.1 会有「只有鼠标能做」的操作；
> 缺 3.2 会有「只有 AI 能触发」的暗道；缺 3.3 会有「删错东西」的事故。

## 4. 三平面架构

控制、观测、开发是三个**正交**的平面。混在一起会导致「改设置」和「改源码」
共用一条无差别的通道——那是把最高风险的操作伪装成最低风险。

```
                  ┌──────────── Agent 闭环（决策层）────────────┐
                  │ 观测 → 对比预期 → 定位 → 改代码 → 编译 → 复测 │
                  └──────┬──────────────────────────┬──────────┘
       控制命令 / 查询     │                          │ 状态 / 事件 / 断言
        ┌────────────────▼──────────┐    ┌──────────▼───────────┐
        │ 控制面 Control Plane      │    │ 观测面 Observability  │
        │ 命令总线（唯一入口）        │    │ 状态快照 / 事件流 /    │
        │ 校验·授权·调度·审计        │    │ 断言结果               │
        └────────────────┬──────────┘    └──────────▲───────────┘
                         │ 调处理器                  │ 状态中心 / 审计
        ┌────────────────▼──────────────────────────┴───────────┐
        │            应用本体：状态中心 + 命令处理器               │
        └────────────────▲───────────────────────────────────────┘
                         │ 读写源码 / 调构建 / 替换产物 / 重启
        ┌────────────────┴──────────────────────────────────┐
        │ 开发面 Dev Plane：快照 → 改码 → 编译 → 测试 → 回滚   │
        └───────────────────────────────────────────────────┘
```

### 4.1 控制面

- **唯一入口**是命令总线：校验 → 授权 → 调度 → 执行 → 写状态 → 审计。
- 人与 AI 走**同一条**。若 AI 有特权通道，那条通道就是没被测过的路径。
- 高频交互（拖拽中的流式位移）**不必逐帧成命令**：松手那一刻生成一条结构化命令
  进撤销栈与审计。这是双轨，不是例外。

### 4.2 观测面（快照 + 事件流 + 断言，三者齐备）

控制面解决「做」，观测面解决「做完怎么知道」。三类能力（均已落地，契约见 §10.2）：

| 能力 | 形态 | 用途 |
|---|---|---|
| **状态快照** | 一次请求返回当前全量状态 | 「现在是什么样」 |
| **事件流** | 状态变更后主动推送 | 「刚才发生了什么」 |
| **断言结果** | 操作附带「应满足什么」，返回是否满足 | 「是否符合预期」 |

**为什么快照不够**：快照只能证明「终态对」，无法证明「中间没出错」。
例如「删除文件」：快照显示文件不在了，但它可能是被移走、被别的进程删掉、
或操作半途失败而文件本就不在。**只有事件能区分这些。**

**事件流已补齐**：服务端检测状态变化后主动推 `state.changed` / `command`，
带全局单调序号，订阅用 `events/subscribe`（同连接先 ack 再推）、断线用 `events/since`
按 `after=lastSeq` 补历史。于是「中间发生了什么」不再靠两次快照猜。

**选中与焦点已补齐（2026-11-21）**：快照新增 `selectionCount` / `selection` /
`selectionFolders` / `selectionTruncated`（枚举上限截断标记）与 `focus`
（`GetGUIThreadInfo` 按窗口祖先链判定焦点落在 file_view / nav_tree / bookmark_bar /
address_bar / unknown）。在此之前的缺口是致命的：`ShellView::SelectedCount()`
内部存在但仅用于命令前置，观测面看不到选中——AI「收藏选中的文件夹」这类需求
只能靠猜（实测踩坑：重启丢现场后把 `D:\` 当成目标写进书签）。同时新增
`bmk.add.selection`（`needsSelection=true`）：AI 先读快照确认选中，再调用收藏，
`check_ai_meta.py` 第 4/14 项保证「观测面读不到选中」时这类命令自动收紧不暴露。
恢复用户上次选中由会话持久化承担（`sessionSelection`）。

### 4.3 开发面

改代码 → 编译 → 测试 → 保留或回滚。三条硬约束：

1. **已经隔离**：测试实例用 `EXBARBROWSER_PROFILE=<目录>` 指定独立配置目录，
   只给 `MULTI=1` 时落到 `data\profile-multi`；所有路径派生自 `Config::Dir()`，
   并在任何配置读写之前切换。契约与双实例文件级验证见 §10.3。
2. **必须可回滚**：改动前有快照（git 提交或 stash），失败能整体丢弃。
3. **必须最严授权**：开发面默认关闭，需人工批准 + 沙箱，不与文件操作共用通道。

## 5. 能力注册表：一份数据，三个消费者

每条操作登记时带齐闭环所需的元数据：

```
type         点分名（唯一标识，机器用它）
category     域（file / view / app / dev）
actor        允许的调用方（human / ai）
effects      只读 / 破坏性 / 幂等 / 跨进程 / 可撤销 / 作用域
argsSchema   参数 schema
outputSchema 返回 schema（可选）
requires     前置条件
query        执行后用什么查结果
events       会产生哪些事件
assertions   执行后应满足什么
```

**同一份数据服务三个消费者**：

1. **给 AI 生成工具清单**：MCP `inputSchema` 直接复用 `argsSchema`，不手写第二份。
2. **给测试生成用例**：每个 Action 自动有「执行 → 查结果 → 等事件 → 跑断言」骨架。
3. **给 UI 做权限与提示**：危险操作的确认、撤销栈、置灰判定都从 `effects` 读。

> **`assertions` 是当前缺的最后一个字段。** 有了它，「可验证」从**脚本层**
> 提升到**契约层**：断言跟着命令走，而不是散落在各测试文件里靠人记得补。

## 6. 为什么「按值」而不是「切换」

对外暴露的操作必须是**幂等设定**，不能是「翻转」。

理由：AI 无法表达「确保它是开的」。若接口是 `toggle`，调两次等于没调，
而 AI 无从知道当前是哪一次。`toggle` 只能是 `set(value)` 的一种**界面用法**
（读现值再取反），不能是对外契约。

同理，**修改类操作必须能读回**。只能写不能读时，`isError=false` 就成了
「改成功了」的唯一证据——而它可能表示「前置条件跳过」「参数取了默认值」
「被用户刚做的操作覆盖」。这类缺陷不会当场报错，只会让人基于错误认知继续。

## 7. 一次完整闭环（模板，不绑定具体功能）

任何操作都套这个形状：

```
① 准备     instance.spawn(profile=test, isolatedConfig=true)
② 定位     nav.open(target=X, section=Y)          ← Navigation
③ 读初态   X.get(key=k)                            ← Query
④ 操作     X.set(key=k, value=v)                   ← Action
⑤ 读终态   X.get(key=k)                            ← Query
⑥ 等事件   subscribe(X.changed)                    ← Event
⑦ 断言     expect(终态 == v) && expect(收到事件)     ← assertions
⑧ 持久化   重启后 X.get(key=k) 仍 == v              ← 分两阶段验证
```

**⑦ 与 ⑧ 缺一不可**：⑦ 证明「这次改对了」，⑧ 证明「真的存下来了」。
只做 ⑦ 会漏掉「改了内存没落盘」——这类 bug 在下次启动时才出现，而那时现场已丢。

**这个模板对文件操作同样适用**：

```
① 准备   instance.spawn(...)
② 定位   nav.open(D:\work)
③ 读初态 file.list(D:\work)
④ 操作   file.move(sources=[a.txt], target=D:\backup)
⑤ 读终态 file.list(D:\work) + file.list(D:\backup)
⑥ 等事件 file.moved
⑦ 断言   a.txt 不在源、在目标
⑧ 持久化 重启后仍然如此（文件系统本身保证，但目录视图要刷新）
```

**同一模板覆盖两类对象**（文件与软件自身），这正是「所有操作」的含义。

### 7.1 把闭环从"模板"变成"一条命令"（ebbctl + 意图目录）

上面的模板此前要靠 Agent 手工执行：读命令表找名字、读 handler 猜参数、读磁盘找
id、另写脚本回读验证。那不叫自动化，只是"知道怎么手动做"。现在把这段编排固化成
**声明式配方**，模板的 8 步收敛为一条意图命令：

```
# 程序用 --ai 启动（不碰 settings.json）；然后：
python tools/ebbctl.py call bmk.list '{}'              # 任何单条命令：统一通道
python tools/intents.py bookmark.move-to-end name=坚果云  # 一个意图：定位→执行→验收
```

四层工具，逐层消灭一类手工操作（对应 §9 的差距逐项转绿）：

| 层 | 解决什么 | 落地 |
|---|---|---|
| **P0 通道自举** | 以前要临时改 `aiEnabled` 再重启，且退出回写会污染用户设置 | `--ai` 开关 / `EXBARBROWSER_AI=1` 只置进程内标志（Config::AiChannelEnabled），**永不写盘** |
| **P1 统一客户端** | 以前每次手写 ctypes 管道客户端、拼 JSON-RPC、处理推送混流 | `tools/ebbctl.py`：发现 pipe/token、call/list/state/events/subscribe 全覆盖，连接带重试 |
| **P2 内置验证** | 以前 `ok=true` 不等于效果对，要另写脚本回读 | 每次响应带顶层 `verdict`（ok + 断言），`ebbctl call --verdict` 一行出判定 |
| **P3 意图目录** | 以前"移到最后"要手工翻译成 list→找 id→move→回读 | `tools/intents.py` 声明式配方表，加意图=加一行；幂等（已在末位则跳过 move） |

**为什么意图放在客户端而不是新增 `intent.run` 命令**：命令总线的 `lastBlockReason_`
是单槽、可重入敏感；handler 嵌套调用会踩掉外层原因。意图本质是**已有命令的编排**，
每步仍走普通 `tools/call`（没有旁路），编排层放统一客户端里既是单一真源，也不引入
可重入缺陷。

**验收**：`tests/e2e/bookmark_move_e2e.py` 用新范式跑完整闭环，覆盖"已在末位"（幂等）
与"从第一位移到末位"（真移动）两种场景，逐项检查 verdict、独立回读、磁盘落盘、
审计、以及 `aiEnabled` 未被改动。

> 已知环境性 flaky：`pipe_e2e_test` 与真实实例共用全局命名管道，连续/并发跑时偶发
> `tools/list` 拿到空集（单连接模型的时序竞争）；单独重跑即通过。这类失败不是功能
> 回归，记为"环境不满足"，不静默算绿也不假装是 bug。

## 8. 分层与授权

| 层 | 对象 | 撤销 | 默认授权 |
|---|---|---|---|
| **L1 文件域** | 磁盘文件/目录 | 移动/改名/复制可回滚；删除进回收站 | 读开放；写/删需确认 |
| **L2 应用域** | 软件自身状态与 UI | 配置可回滚 | 开放（低风险） |
| **L3 开发域** | 功能与代码 | 弱：需快照 + 卸载 | **默认关闭，需人工批准 + 沙箱** |

**关键区分**：「操作软件本身」≠「改软件代码」。L2（配置、布局、主题、列设置）
与 L3（改源码、编译、热加载）风险差三个数量级，不能共用一条通道。

持有时 `OpenClipboard` 返回 `err=5`（用 ctypes 直接调同样失败），测试记为
「无法运行」而非「失败」—— 环境不满足不能当成实现缺陷，也不能假装通过。

## 10. 落地顺序（按依赖，不按价值）

1. ✅ **`assertions` 字段**：命令表第十个字段，选中高频写命令先补；
   检查器第 18 项校验「有断言就必须能求值」（左值在状态里、`$arg:` 在 schema 里）。
2. ✅ **设置数据化**：`config.list` / `config.get` / `config.set` 三条命令 + 键表
   `settings_reg`（32 项）+ 设置面板。契约见 §10.1。
3. ✅ **事件流**：`events/subscribe` 推 `command` / `state.changed`，`events/since` 补历史。契约见 §10.2。
4. ✅ **测试隔离**：`EXBARBROWSER_PROFILE` 指定目录，`MULTI=1` 默认 `data\profile-multi`。契约见 §10.3。
5. ✅ **开发面**：快照 + 编译 + 测试 + 作业回读 + 回滚。契约见 §10.4。

> 顺序的理由：前四项都是**让判据成立**，第五项是**让 Agent 自主使用判据**。
> 判据不成立时做自动化，只会让错误自动扩散。

### 10.1 设置层的契约（键表 = 界面 = 命令 = AI）

设置是「程序操作自身」的最小样本：一个值、一个名字、一次写入、一次回读。
它跑通了，别的可调状态照同一条路走。

| 契约 | 落地 | 为什么必须这样 |
|---|---|---|
| **一个名字** | `key` 用 `settings.json` 里的键名（`tab` / `viewMode` / `window.x`） | 用户手改文件、AI 调命令、界面显示用的是同一个名字；三套名字迟早对不上 |
| **一个读路径** | `settings_reg::Get` → Entry 的 `get` | 界面上每行、`config.get`、AI 决策读的是同一份活状态，不是配置副本 |
| **一个写路径** | `settings_reg::Set` → Entry 的 `set` → **写后回读比对** | 赋值跑过 ≠ 状态变了；读背能让「写了 A 字段、读了 B 字段」当场暴露 |
| **拒绝要带原因** | 不存在 / 只读 / 类型不符 / 超范围，四种说法各不相同 | 「set 失败」对调用方没有信息量；名字错和值超范围该做的下一步完全不同 |
| **只读要说明出口** | `set` 为空 = 只读，`doc` 写清该用哪个入口 | 窗口几何、会话、键位这些项「改了不生效」，与其造半成品写入口，不如说清 |
| **人机同源** | 设置面板（视图菜单「设置…」）调 `config.get` / `config.set` | 面板不直接改字段，于是面板上每次改动都有审计、都过同一份校验 |
| **写完推给界面** | `config.set` 之后按 key 刷新（`SyncChrome` / `ApplyPersistedViewState`） | 只写配置不改活状态，就是「改了看不见效果、重启才发现」那类 bug |

自检：`settings_reg::SelfCheck()` 逐项「用当前值写回」，任何一项 set 忘接线都会被抓出来
（`tests/settings_reg_test.cpp` 把它当断言）。

> 一条实测：`config.set viewMode=6` 最初只改了配置，`state.viewMode` 仍是旧值——
> 因为 `viewMode_` 是 App 的活状态，只有 `ApplyViewMode` / `ApplyPersistedViewState`
> 会更新它。修法是让后者也赋值 `viewMode_`，而不是在 config.set 里再抄一遍。

**验收（真实命名管道，非模拟）**：`config.list` 32 项无重名；`config.get/set` 改后回读一致；
越界 `viewMode=9`、未知键、只读键 `window.x`、布尔项给整数，四种拒绝都带各自原因；
`config.set viewMode=6` 后 `state.viewMode` 同步变成 6，`config.set bookmark=false` 后
`state.bookmarkBarVisible` 同步翻转——证明「写配置」确实推到了活状态，而不只是落盘。
全量 `tests/run_all.sh` 39/39 通过，三项静态检查通过。

**命令面板（R20）随之修正**：旧规则把「带必填参数」的命令整条从面板剔除，导致
`config.get/set`、`file.rename` 等只有 AI 能触发。现在面板列出所有已实现命令，
无必填参数走空参、有必填参数按 `argsSchema` 追问后再调用——既不空参清空别名，
也没有人类侧不可达的命令。检查器第 15 项同步升级为这两条判据。

### 10.2 事件层的契约（序号 = 续接点，不是装饰）

轮询只能回答「现在是什么样」，回答不了「刚刚发生了什么」：两次采样之间发生又恢复的变化
会被整个漏掉。事件流补的是这一块，**不是**替代 `state` 快照。

| 契约 | 落地 | 为什么必须这样 |
|---|---|---|
| **全局单调序号** | 每条事件带 `seq`，从 1 起递增 | 断线重连靠 `after=lastSeq` 精确续接；没有序号就只能全量重扫 |
| **先确认后推送** | `events/subscribe` 先回 ack，再在同一连接上推事件 | 服务端单连接模型；另开连接发命令会被 `ConnectNamedPipe` 挡住 |
| **历史可补** | `events/since?after=N` 返回增量 + `lastSeq` | 客户端重启后不该从头猜；缓冲淘汰时回 `gap=true` 明说漏了 |
| **缓冲有上限** | 512 条环形缓冲 | 历史事件是诊断材料，不是数据库；不能让订阅者拖垮内存 |
| **服务端检测状态变化** | UI 定时器比较 `StateToJson()`，变了才发 `state.changed` | 客户端不必自己定轮询频率；推送仍是事实，不是猜测 |
| **拒绝也有事件** | `Call()` 包住整个执行体，未知命令/需批准/参数非法都发 `command` | 只记录"进入总线的调用"会漏掉最该被看到的一类失败 |
| **事件带参数与断言** | `command` 事件含 `args` / `assertions` / `verdict` | 「调了什么、结果对吗」要能从事件单独还原，不必再去翻审计 |

订阅行带 `{"event":true,...}`，与请求响应在**同一条连接**上靠这个字段区分。
`events/since` 与 `events/subscribe` 同时提供本地简格式与 JSON-RPC 两种形状，
令牌校验与命令通道共用，没有给事件开旁路。

**验收（真实管道）**：订阅后执行 `config.set viewMode=4`，收到序
`state.changed(5) → command(config.set) → state.changed(4)`；
命令事件里 `ok=true`、参数 `{"key":"viewMode","value":4}`，紧随其后的状态事件里
`viewMode=4`。序号单调唯一。检查器第 19 项已用「故意改名 PollStateChanges」验证能真失败。

### 10.3 测试隔离的契约（第二个实例不能碰用户数据）

`MULTI=1` 让实例落到 `data\profile-multi`（不再与用户数据同目录），
`EXBARBROWSER_PROFILE=<目录>` 可指定任意独立目录。判据不是"能不能起第二个窗口"，
而是"用户数据与测试数据的文件是否物理分开"。共享同一份 `settings.json` 的多实例
之所以安全，是因为写盘走原子写（`<file>.<pid>.tmp` + `MoveFileEx(REPLACE_EXISTING)`），
后写不会截断前写。

| 契约 | 落地 | 为什么必须这样 |
|---|---|---|
| **一个环境变量** | `EXBARBROWSER_PROFILE=<目录>` 显式指定；只给 `MULTI=1` 时落到 `data\profile-multi` | 测试能用固定目录，也能并发开多个不同目录 |
| **启动最早一步** | `main.cpp` 在读取/写入任何配置之前切换目录 | Config 是懒加载；晚一步就会先把用户配置读进内存 |
| **所有路径派生** | 设置/书签/键位/鼠标/审计/AI 管道与令牌全部走 `Config::Dir()` | 只要有一处硬编码 `data\`，隔离就是假的 |
| **换目录即清空内存态** | `SetProfileDir` 重置 `Settings` 与 `loaded_` | 否则 B profile 启动时会把 A 的会话/热键写回去 |
| **文件级验证** | 单测写 a、切 b、再写 b，断言两份文件内容不同 | "路径看起来不同"证明不了没覆盖，要读回文件比对 |

**验收（真实双实例）**：`EXBARBROWSER_MULTI=1 EXBARBROWSER_PROFILE=...\profile-e2e`
启动的实例从自己的 `settings.json` 读到 `viewMode=2`，`config.set` 改成 3 后只有
该 profile 的文件变化，用户 `data\settings.json` 的 SHA-256 前后一致。检查器
第 20 项已用「把 profileBuf 换成空串」验证能真失败。

### 10.4 开发面的契约（Agent 能自己用前四层的判据）

前四层把「操作可验证」做成了事实，但 Agent 还不会自己用：它得拿到现状、改代码、
编译、跑测试、读结果，错了还能退回。这五条命令把这条链收进同一条命令总线 ——
人从命令面板可达，机器从 AI 通道可达，没有第二套实现。

| 契约 | 落地 | 为什么必须这样 |
|---|---|---|
| **先快照再动手** | `dev.snapshot` 返回 HEAD / 脏文件列表 / diff 统计 / profile 目录 | 没有「改之前什么样」，回滚就没有基准，也无法判断是否误改了别人的文件 |
| **耗时操作异步** | `dev.build` / `dev.test` 立即返回 `jobId`，完成时推 `dev.job.done` 事件 | 在 UI 线程等编译会卡死窗口；有了事件流也不该让客户端轮询 |
| **结果可回读** | `dev.job` 读回 `done` / `exitCode` / `output` | 事件可能丢，回读是兜底；两者形状一致才能互证 |
| **复用仓库脚本** | 底层仍是 `build_fast.py` / `tests/run_all.sh` / `git` | 另写一份"AI 专用构建"必然与人工构建分叉，最后测试 green 的是假代码 |
| **回滚要校验路径** | 拒绝对路径 / 盘符 / `..` / 命令分隔符 / 未修改文件 | `git checkout --` 是真正会丢数据的命令，不能靠调用方自律 |
| **人侧等价确认** | 命令面板对破坏性命令弹确认；AI 侧仍需 `approve=true` + `aiAllowDanger` | 面板直接走 CommandBus，不补这一步就成了绕过批准的后门 |

**验收（真实管道）**：`dev.snapshot` 拿到当前 HEAD；订阅后调 `dev.test {filter:"events"}`
得到 `jobId=job-4`，收到 `dev.job.done` 事件（exitCode=0，输出含 `PASS events_test`），
`dev.job` 回读一致；`dev.rollback {path:"../evil"}` 带 `approve=true` 仍被路径校验拒绝。
检查器第 21 项已用「去掉人侧确认判据」验证能真失败。

至此五层全部落地：assertions（判据）→ 设置数据化（操作自身）→ 事件流（反馈）→
测试隔离（安全试验场）→ 开发面（自主闭环）。`docs/FULL-COVERAGE.md` 里的差距表
已逐项转为 ✅。

## 11. 不做的事

| 不做 | 原因 |
|---|---|
| 给 AI 开特权通道 | 那条路没被验证过，等于给自己留后门 |
| 为 AI 单独写一份实现 | 必然与 UI 那份分叉，而分叉只在事故时暴露 |
| 用「尽力而为」兜底参数 | 静默丢弃参数比报错危险得多 |
| 暴露依赖隐式上下文的操作 | AI 不知道用户选了什么，暴露即让它猜 |
| 用模拟输入做验收 | 有假通过风险，测试失去证明力 |
| 用快捷键做自动化 | 是输入绑定，改键位即失效 |

## 12. 参照（各层都有成熟样本，但没有把它们焊到文件管理器上的）

| 层 | 参照 | 可抄什么 |
|---|---|---|
| 控制+观测 最接近 | Blender + `blender-mcp` | 一切操作皆 operator，UI 与脚本同路径；socket 双向推事件 |
| 工具分级+回归 | `blender-mcp-ultra` | typed 工具、AST 黑名单、CI 跑真实 E2E |
| 命令总线 | swissarmyhammer / Baserow | `dispatch_command` 单一路径；Action 落库含 undone_at/error |
| 编辑器范式 | VS Code | `registerCommand` + `getCommands` 可枚举；独立 profile 测试实例 |
| 自改代码闭环 | Darwin Gödel Machine / OpenEvolve | patch validation、沙箱、择优保留 |
| 撤销栈 | `ktsu.UndoRedo` / `Atc.UndoRedo` | 命令合并、组合命令、审批否决 undo |

**真正的空白**：没有开源文件管理器内建这套契约。控制面模式在 Blender/VS Code，
开发面在 DGM/OpenEvolve，但「文件管理器 × 程序化契约 × 自改闭环」没有现成项目。

---

## 13. 一句话总结

> 架构上真正难的不是「加一个接口」，而是**让状态可观测、让路径唯一**。
> 前者决定 AI 能否判断，后者决定判断是否可信。
> 缺任何一半，闭环都只是自动化，不是改进。
