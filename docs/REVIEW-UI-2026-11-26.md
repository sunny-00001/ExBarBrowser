## 2. 问题明细

### 2.1 P0(严重:可致崩溃或视觉永久错乱,必须修)

#### [P0] UI-S1　模态弹层开着时收到主题/DPI 变更,弹层借用的 HICON / HFONT 被销毁

- **文件**:`src/popup_list.cpp:751-757`;关联链 `src/app_wnd.cpp:192-208`、`src/app_layout.cpp:302/322`、`src/status_bar.cpp:70`、`src/sys_icon.cpp:65-72`、`src/app_commands.cpp:465/475`、`src/menu.cpp:41-49`、`src/theme.cpp:204-209`
- **符号**:`popup::RunModal`(模态消息泵)、`App::ApplyTheme`、`StatusBar::ReloadTheme`、`sysicon::Invalidate`、`Menu::AddSystemIcon`、`Theme::Reload`
- **问题**:状态栏右键菜单等模态弹层开着时,系统发生主题/高对比度/DPI 变化,主题系统销毁弹层正在借用的 HICON/HFONT,弹层继续用悬空句柄绘制。
- **机理**(已逐段确认):
  - `popup_list.cpp:751-757` 的模态泵 `while (!st.done && (gm = GetMessageW(&msg, nullptr, 0, 0)) > 0) { TranslateMessage; DispatchMessageW; }` —— **对全部消息一视同仁**,含 `WM_SETTINGCHANGE` / `WM_THEMECHANGED` / `WM_DPICHANGED`。
  - `app_wnd.cpp:192-203`(SETTINGCHANGE)与 `app_wnd.cpp:206-208`(THEMECHANGED)→ `App::ApplyTheme`(`app_layout.cpp:302`)→ `statusBar_.ReloadTheme()`(`app_layout.cpp:322`)→ **`status_bar.cpp:70` `sysicon::Invalidate()`** → `sys_icon.cpp:65-72` 对缓存句柄逐个 `DestroyIcon`。
  - 而状态栏右键菜单的行图标正是借用这些句柄:`app_commands.cpp:465` `menu.AddSystemIcon(kSegNames[i], on, i, sysicon::Get(StatusSegmentSysId(i)), …)`,`menu.AddSystemIcon` 把 HICON 直接存进 `PopupRow::icon`(`menu.cpp:41-49`,注释明确"借用,菜单不销毁")。菜单在 `app_commands.cpp:475` 进入模态。
  - 于是:**菜单开着 → 系统切深浅色(或高对比度)→ 弹层继续用已 DestroyIcon 的句柄绘制**(`popup_list_draw.cpp:85-87` `ui::DrawIconCentered` → `DrawIconEx`)。轻则该行图标消失,重则 GDI 句柄复用后画到别的对象上/访问违例。
  - 同一路径还有第二个坑:`theme_.Reload` 在 DPI 变化时删字体(`theme.cpp:204-209`),而弹层的 LISTBOX 在 `popup_list.cpp:678` 用 `WM_SETFONT` 挂过一次字体句柄,之后不再重设 → 后续 `WM_DRAWITEM` 可能把已删除的 HFONT 选进 DC。
- **可达性**:菜单开着时按 Win+ 切系统主题、或把窗口拖到另一块不同缩放比例的屏,都是日常操作;不需要脚本或调试器。当前唯一的安全边界是"主题切换只由用户点击触发"——这是**靠用户行为而不是靠代码**保证的,一旦有脚本/自动化/AI 命令能触发 `ApplyTheme`,就立刻变成悬空句柄。
- **建议修法**(二选一,建议都做):
  1. 弹层模态泵过滤主题/DPI 消息:在 `RunModal` 的循环里对 `WM_SETTINGCHANGE`(`l` 为 `ImmersiveColorSet`/`HighContrast`/`WindowsThemeElement`)、`WM_THEMECHANGED`、`WM_DPICHANGED` 只置 `st.themeChanged = true` 并 `continue`,循环结束后 `InvalidateRect(owner)` 让主窗口自己去处理(消息不会丢语义,只是延后一帧)。
  2. `status_bar.cpp:70` 的 `sysicon::Invalidate()` 加守卫:`if (modal::Depth() == 0) sysicon::Invalidate();`(`modal.h:41` 的 `Depth()` 就是为这类"模态期间别动共享资源"准备的,弹层也已经在 `popup_list.cpp:751` 登记了 `modal::Scope`)。同理,任何 `ico::ClearCache()` 也应加同一守卫。
  - 改动量约 10 行,收益最大,建议最先修。

### 2.2 P1(中:功能/视觉可复现缺陷,或明显性能/资源浪费)

#### [P1] UI-S2-1　状态栏段丢弃链耗尽后无兜底,左右两组会重叠

- **文件**:`src/status_bar.cpp:167-308`
- **符号**:`StatusBar::Layout`(`kDropOrder` 在 `:229`,守卫循环 `:232/:244`,左组排布 `:267`,右组回填 `:297-303`)
- **问题**:窄窗口 + 长目录名 + 全段开启时,左组宽度总和(已无段可丢)会越过右组的左边界 → 两组文字互相压字。
- **机理**:`kDropOrder`(`:229`)依次丢掉 Type/Eye/Disk/Size/Date;`for (int guard = 0; guard <= Seg_Count; ++guard)`(`:232`)在"无可丢"时 `break`(`:244`)。此后**没有**任何"进一步压缩"或"拒绝右组"的分支:左段按 `x += w + gap`(`:267`)直接向右排,右组按 `rc.right - pad` 回填(`:297-303`)。`Paint`(`:345-369`)按 `layout_` 原样画,没有相交裁剪。
- **建议修法**:丢弃链结束后若 `leftW + rightW + (showPath ? S(120) : 0) > avail`,再走一级降级(右组只留图标、或把 `Seg_Chk/Seg_Date` 也纳入丢弃链),并在 `Layout` 末尾对 `layout_` 做一次"右组左边界不得小于左组右边界"的夹取;`app_stats`/单测加一条"极窄窗口不重叠"的断言(`side_layout`/`pane_split` 都有纯函数单测,这里缺)。

#### [P1] UI-S2-2　弹层高度夹进工作区,宽度没夹

- **文件**:`src/popup_list.cpp:641-651`
- **符号**:`popup::RunModal`(定位与夹取段;`PopupMeasureWidth` 见 `popup_list_draw.cpp:160-172`,`exactWidth` 分支 `:188-189`)
- **问题**:`width > 工作区宽` 时,`x` 夹到 `rcWork.left`,右半截落在屏幕外,且**滚动条也在屏幕外**——正是 `:634-639` 注释里描述的同一类坑(那条注释只解决了高度)。
- **机理**:`if (height > workH) height = workH;`(`:641`)有;宽度只在 `:645-646` 做 `x` 的回退夹取:`if (x + width > mi.rcWork.right) x = rcWork.right - width; if (x < rcWork.left) x = rcWork.left;`。`PopupMeasureWidth` 上限是 `theme.S(460)`,但 `exactWidth` 分支(`popup_list_draw.cpp:188-189`)直接用调用方给的 `minWidthPx`;多显示器 + 窄副屏时 460dp@200% = 920px 已可超。
- **建议修法**:与高度对称地加 `if (width > workW) width = workW;`(放在算 `x` 之前),同时让 `PopupMeasureWidth` 的 `exactWidth` 分支也受 `workW` 约束。

#### [P1] UI-S2-3　状态栏右键与左键报的 target 不一致(`MT_STATUS` vs `MT_STATUS_SEG`)

- **文件**:`src/status_bar.cpp:137`(DOWN 分支 `:118-120`,左键 UP `:128`)
- **符号**:`StatusBar::WndProc` / `WM_RBUTTONUP` 分支、`HitSegment`
- **问题**:`mouse.json` 里按"状态栏段"配的右键规则永远命中不到(`:117` 的注释声称已修好,实际只修了左键/中键);且同一次物理右键的 DOWN 与 UP 带不同 target,依赖"DOWN+UP 成对"的规则会失效。
- **机理**:`WM_LBUTTONDOWN`/`WM_RBUTTONDOWN`/`WM_MBUTTONDOWN` 分支(`:118-120`)按 `HitSegment(...) >= 0` 报 `MT_STATUS_SEG`,`WM_LBUTTONUP`(`:128`)同样按段报;但 `WM_RBUTTONUP`(`:137`)**恒报 `MT_STATUS`**,不看段。
- **建议修法**:`WM_RBUTTONUP` 改为 `HitSegment(pt.x, pt.y) >= 0 ? MT_STATUS_SEG : MT_STATUS`(与左键同一条表达式,抽成局部 lambda 免得又漂一次)。

#### [P1] UI-S2-4　菜单构建期同步解析图标,长菜单首开可感知卡顿

- **文件**:`src/menu.cpp:51-59`;链路 `src/icon_resolve.cpp:205-266`
- **符号**:`Menu::AddPath`(`ico::Cached(path, true)` 在 `:55`)
- **问题**:历史下拉/书签菜单 20+ 行 = 20+ 次 shell 解析,全部在 UI 线程、在"点击到弹出"之间;SSD 上约 1~3ms/条,机械盘或网络路径可达几十 ms/条 → 菜单"点了半秒才出来"。`Cached` 只在同一次会话内缓解。
- **机理**:每个路径行在 `Add` 时就 `ico::Cached(path, true)`(`:55`);冷缓存下每条会走 `icon_resolve.cpp:205-266` 的完整链路(`SHParseDisplayName` → `SHGetFileInfoW(PIDL)` → 兜底注册表 → stock)。
- **建议修法**(择一):(a) 先用 `ico::IconId::Folder`/同类字形占位,弹层画出后由空闲回调替换;(b) `Menu` 只存 path,图标在 `Show` 里逐行取并在后台线程预热(`ico::Cached` 需要加锁或改 per-thread);(c) 至少把这条路收进启动期预热(历史/书签读盘后批量 `ico::Cached`)。

#### [P1] UI-S2-5　上下文菜单每行都按整表量一次宽,O(n²)

- **文件**:`src/menu_context.cpp:123-137`;量宽实现 `src/popup_list_draw.cpp:160-172`
- **符号**:`MenuContext::OnMeasureItem`、`PopupMeasureWidth`、`MeasureText`
- **问题**:右键菜单"弹出到可见"多几十 ms;属纯浪费(整表宽度在同一轮里是常量)。
- **机理**:`item->itemWidth = PopupMeasureWidth(nullptr, *theme_, &drawRows_, nullptr, …, false, 0)` —— 对**每一行**都遍历整表 + 每行各 `MeasureText`。22 行菜单 = 约 484 次 `GetTextExtentPoint32W`,且每次都 `GetDC(nullptr)`/`ReleaseDC`。
- **建议修法**:`QueryContextMenu` 里算一次存成员 `itemW_`,`OnMeasureItem` 直接用它(`QueryContextMenu` 与 `MEASUREITEM` 之间 `drawRows_` 不变,安全)。

#### [P1] UI-S2-6　状态栏每次刷新全量重建全部 tooltip tool,`MoveTools` 却没用

- **文件**:`src/status_bar.cpp:307`(链路 `:51-57` SetModel → Layout → RebuildTooltip `:310-323`);`src/tooltip_host.cpp:83`(`Clear`)、`:70-104`(`SetTools`)
- **符号**:`StatusBar::RebuildTooltip`、`TooltipHost::SetTools`、`TooltipHost::MoveTools`
- **问题**:状态栏模型在选文件/切目录/定时器里频繁更新 → 每秒数十次重建;每次 14~18 次跨窗口消息。
- **机理**:`SetModel`(`:51-57`)→ `Layout` → `RebuildTooltip`(`:310-323`)每次都 `tooltip_.Attach` + `tooltip_.SetTools(items)`,而 `SetTools` 内部先 `Clear()`(`tooltip_host.cpp:83`)→ 逐个 `TTM_DELTOOLW`,再逐个 `TTM_ADDTOOLW`(`:70-104`)。段数 7~9。而 `TooltipHost::MoveTools`(`tooltip_host.h:46`,已由 `tab_strip_layout.cpp:197` 使用)正是为这种"文本没变、只有矩形变"的场合准备的。

#### [P1] UI-S2-7　prompt 键盘可达性:ESC/Enter 只在焦点位于 EDIT 时生效

- **文件**:`src/prompt.cpp:162-173`(单字段 `onKey`)、`:233-252`(双字段)
- **符号**:`PromptText` / `PromptText2` 的 `onKey` 回调
- **问题**:焦点一旦落到"确定/取消"按钮(用户拖动窗口、或点了按钮又改主意、或 Tab 到按钮),ESC 取消/Enter 确认失效,走 `DefWindowProc`(`WS_SYSMENU` 下 ALT+F4 可用,但 ESC/Enter 语义丢失)。顺带:单字段版**完全没有** Tab 处理(`:162-173` 只处理 RETURN/ESCAPE),双字段版的 Tab(`:244-250`)只在两个 EDIT 之间来回,永远到不了按钮;两版都没有 `IsDialogMessage` 或 Tab 序。

- **建议修法**:`onKey` 的判定改成"消息属于本对话框(`msg.hwnd == hwnd` 或其子窗口)"而不是枚举具体控件;Tab 用 `GetNextDlgTabItem` 或干脆在循环里调 `IsDialogMessageW(hwnd, &msg)`(它自带 Tab/Enter/ESC 语义,`modal.h:23-24` 的 `onKey` 约定也允许)。

#### [P1] UI-S2-8　`radiusPopup` 是死令牌,且与弹层现实矛盾

#### [P1] UI-S2-9　三个画刷建了、删了、从没用过;高频路径反而在现建刷

- **文件**:`src/theme.cpp:143/:148/:149`(`Theme::Init` 创建)、`Theme::Shutdown` 删除;`src/theme.h:171/:176/:177`(字段声明);对照 `src/ui_draw.cpp:118-122`
- **符号**:`Theme::brPressed` / `Theme::brSelSolid` / `Theme::brAccent`、`ui::FillRectColor`
- **问题**:每次 `Reload`(切主题/DPI)多 3 次 `CreateSolidBrush` + 3 次 `DeleteObject`;且与 `ui_draw.cpp:118-122` 的 `FillRectColor`(每次调用临时建刷/删刷)形成"有刷不用、用时现建"的反向浪费——`popup_list_draw.cpp:58/61`、`status_bar.cpp:349/373`、`split_bar.cpp:283` 都在高频路径上现建刷。

## 4. 按维度的结论

**1. 视觉来源唯一(通过,2 条例外)**
本组 40 个文件**无一处硬编码颜色**——`grep -rn "RGB("` 只命中三处合法点:`ui_palette.h`(令牌表本体)、`theme.cpp:245`(`Mix` 的 `RGB()` 组装)、`ui_draw.cpp:248-249`(WCAG 兜底的纯黑/纯白,不属于调色)。**无一处自建字体**:`CreateFontW/IndirectW` 只在 `ui_draw.cpp:39`(字形字体池)与 `theme.cpp:169-183`(正文/等宽)。字号/栏高/圆角/图标尺寸全部走 `Theme` 成员或 `S()`。例外两条已报:`split_bar.cpp:259-262` 的 `GetSysColor` 兜底(不可达但存在,S3-19),`theme.h:69` 的 `radiusPopup`(无人消费的承诺,S2-8)。

**2. 绘制(GDI 卫生通过;两处资源/缩放缺口)**
本组除 `ui_draw.cpp` 外**零** `CreateSolidBrush/CreatePen/CreateFont/CreateCompatibleDC`(grep 证实);`DrawTextRow`/`MeasureText`/`MeasureTextHeight` 全部"选字体→无条件还原"(`ui_draw.cpp:190-194`、`:201-205`),`DrawGlyph` 还额外 `SaveDC/RestoreDC`(`:66/:73`)。双缓冲:`split_bar`/`status_bar` 走 `ui::PaintBuffered`,弹层走 `WS_EX_COMPOSITED`,`prompt` 直画(可接受)。缺口:`PaintBuffered` 的位图泄漏路径(`:272-283`,S3-10)、1px 边框未缩放(`popup_list.cpp:555-562`、`split_bar.cpp:271-276`,归入 S3-25 相邻口径;修法:`std::max(1, theme->S(1))`,96dpi=1、200%=2)。裁剪区:`PaintBuffered` 不读 `ps.rcPaint`(全客户区重绘),本组窗口都是窄条,可接受。

**3. popup_list(核心状态机质量高,1 高危 + 2 中)**
- 命中:`LB_ITEMFROMPOINT`(`:98-102`)+ `PopupExpanderRect`(`popup_list_draw.h:55-64`)"画与点共用同一矩形",是本组最扎实的设计之一。
- 溢出:**高度**夹进 `rcWork` 且顺序正确(`:634-641`,注释解释了"先夹高度再算 y"的坑);**宽度**没夹(S2-2)。
- 模态消息泵:`GetMessageW` 三分支(`>0/0/-1`)处理正确(`:754-758`),`modal::Scope` 正确登记(`:751`);但泵对主题/DPI 消息无防护(S1)。
- 焦点:`SetFocus(st.list)`(`:731`)+ 捕获模型(`:744`)——`SetForegroundWindow`(`:730`)**确认是 UI 触发**:`ShowPopupList`/`ShowFolderTree` 全工程只被 `ui::Menu::Show`(`menu.cpp:137`)与 `folder_tree.cpp:31` 调用,全部由鼠标/键盘交互进入,无脚本、无 AI 命令直接调用路径。属 src 内允许范围。

**4. menu / menu_context(命令身份链路合规)**
菜单行只声明 `CmdId`(`menu.h:122-127`),文案在 `Show` 时由注入的解析器现取(`menu.cpp:108-121`),解析器实现方按 `FindCommand(CmdId)` 反查(`commands.h:110`、`key_binding.h:67`)——**本组没有任何"按字符串解析命令名"的路径**,符合要求。`menu_context.cpp` 只做 owner-draw 桥接与 `data` 回传(`:109-115`),不猜命令名,`HIWORD(lpVerb) != 0` 时拒绝字符串动词(`:111`)——正确。

**5. 内存/资源/编码(良好,细项见上)**
- HICON:`ico::Cached`/`sysicon::Get` 都是"进程级持有、调用方只借",`PopupRow::icon`/`TreeNode::icon` 的注释都写明不销毁;`popup_list.cpp:768-773` 的 `ClearTree` 从"销毁每个 icon"改成"只清结构",注释解释了不这么改会拿到悬空句柄 —— 这条纪律执行到位。唯一破口是 S1(主题切换销毁借用中的句柄)。
- HFONT:唯一来源 `Theme`,`Reload` 在 DPI 未变时保字体(`theme.cpp:217-227`),理由(SHAutoComplete 重建 110~170ms)写清了。
- 字符串/编码:本组全部 `std::wstring`,UTF-8/UTF-16 转换只在 `text_file.cpp`/`str::` 边界;`ReadText` 三种 BOM 都认,UTF-16LE 分支用 `memcpy` 而非 `reinterpret_cast` 避免 ARM64 未对齐读(`:56-57`)——细节到位。`WriteText` 的"pid 后缀 tmp + FlushFileBuffers + MOVEFILE_WRITE_THROUGH"三点理由与实现一致(`:90-127`)。
- 空指针:`prompt.cpp` 对 `st.edit` 可能为 NULL 的情况未判就 `SendMessageW`(`:160`、`:231`)——`SendMessageW(NULL,…)` 是 no-op 不会崩,但建议判一下,否则 `EM_SETSEL` 静默失效时很难查。

**6. 工程约束(通过)**
- 命名空间:`ui::`(绘制/菜单/提示)、`ico::`、`sysicon::`、`popup::`、`modal::`、`panesplit::`、`sidelayout::`、`tf::`、`viewmode::`、`thememode::` —— 无 `eb::` 残留、无匿名全局符号外泄(`namespace {}` 用得规整)。
- 品牌串:`ExBar` 只出现在注释里说明来历(`theme.cpp:93`、`popup_list.cpp:80`),标识串唯一来源仍是 `identity.h`(本组只 `using id::kPopupClass/kPromptClass/kStatusBarClass`)。
- 文件行数:`popup_list.cpp` **844 行**,与 `data/file-length-baseline.json` 记账值一致(棘轮允许,未越界),但它仍是全工程第 6 长、且 AGENTS §3 的 500 行目标未达成;`popup_list_draw.*` 的拆分方向正确,建议下一步把 `ListSubclass` 的输入状态机(type-ahead/键盘/命中,约 300 行)再拆一个 `popup_list_input.cpp`。
- 硬编码中文("确定"/"取消"/菜单文案)与全工程一致,未见 i18n 层,不报。

**7. 死代码/注释(已逐条列在 2.3 节)**
6 处注释与实现不符(含 2 处"两段注释互相矛盾")、3 处死代码块/死 API、3 个死画刷 + 1 个死令牌。集中成因是**实现改了、解释没跟着改**(`theme.cpp` 的底色调平、`popup_toggle` 的捕获时序、`popup_list.h` 的 API 改名)。这类"注释承诺"在本工程里被当作设计约束用(多处注释写着"这正是 X 的成因"),所以失真比一般项目更值钱。

## 5. 总体评价与修复顺序

**本组质量高于平均水平,主要原因是"每处取舍都留下了可核对的原因"**:`popup_list` 的"再点即收"、`pane_split` 的"百分比分母是 content 不是 avail"、`text_file` 的"tmp 名必须带 pid + 必须 FlushFileBuffers"、`sys_icon` 的"序号资源不是稳定 API"、`theme` 的"切主题前先拆 EBC"——这些注释不是复述代码,而是记录了**为什么不是另一种写法**,且能被当前实现一一验证(除 2.3 节列出的 6 处外全部成立)。这类文档密度在 6000 行规模上是真正的资产。

**风险集中在两处:**
1. **模态弹层与全局资源生命周期的交叉(S1,P0)**。弹层是"借用 + 模态长驻"的组合,而它借的东西(HICON/HFONT/画刷)由主题系统在任意时刻销毁重建。当前唯一的安全边界是"主题切换只由用户点击触发、用户不会在菜单开着时切主题"——这是**靠用户行为而不是靠代码**保证的,一旦有脚本/自动化/AI 命令能触发 `ApplyTheme`,就立刻变成悬空句柄。`modal::Depth()` 已经存在(正是为这类问题设计的),但只用来挡 AI 派发,没用来挡资源销毁——这是最值得先修的一条。
2. **纯几何文件的"看起来有防御、其实不可达"(S2-8/S2-9/side_layout 死块/S2-1)**。`side_layout.cpp` 的 24-31 行、`theme` 的三个死画刷、`radiusPopup` 令牌,都是"写了一个正确但永不执行的保障",读者会以为边界已被处理。这类代码比缺失更危险:它让人**不去查**真正的溢出点(`status_bar` 左右组重叠就是真溢出处,S2-1)。

**建议的修复顺序**:
1. **S1(P0)**:一条守卫 + 一条消息过滤,改动 10 行内,收益最大;
2. **S2-1 / S2-2(P1)**:两处真实几何溢出,各 5~10 行 + 单测;
3. **S2-3(P1)**:一行表达式,且是 `mouse.json` 规则失效的真因;
4. **S2-9 + 间距令牌(P1/P2)**:视觉来源唯一性的收尾,顺带消掉高频 Create/Delete 画刷;
5. **S2-10 / S3 系列(P1/P2)**:`gm = 1` 一行修;注释校准纯文档可批量做,建议顺手把"注释承诺"全部再对一遍实现。

**可以延后的**:S2-4/S2-5/S2-6(性能,量级几十 ms,不影响正确性)、S2-11(`prompt` 两版合一,属重构)、`popup_list.cpp` 再拆 300 行(棘轮未超,不阻塞)。
